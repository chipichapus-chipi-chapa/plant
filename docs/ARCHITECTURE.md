# Архитектура

## Общая схема

```
Браузер ── React UI (панели, диалоги, формы)
   │        └─ GardenCanvas: свой рендер тайлов на Canvas 2D
   │  fetch /api/*  (в dev — через прокси Vite)
   ▼
Spring Boot (REST, Bean Validation, ошибки в формате Problem Details)
   ├─ player   — профиль и текущий игрок
   ├─ habit    — привычки и их выполнения
   ├─ economy  — росинки, инвентарь, магазин
   ├─ garden   — карта сада и размещённые объекты
   └─ content  — каталог растений и предметов (данные, а не код)
   ▼
PostgreSQL (схема только через Flyway; CHECK и UNIQUE — последняя линия защиты)
```

**Главный принцип:** клиент только сообщает о намерении («отметь привычку», «купи семя», «посади на (3,4)»).
Дату, награду, цену, стадию роста и баланс считает сервер, а клиенту возвращает новое состояние.

## Принятые решения

### 1. Свой рендер на Canvas 2D вместо Phaser
В MVP сад — это сцена, с которой работают мышью: наведение, выбор клетки, посадка, клик по объекту.
Хождения персонажа, физики и камеры нет. Для этого хватает тайловой карты, атласа спрайтов и целочисленного масштабирования.
Phaser живёт в собственном цикле со своим состоянием, и его пришлось бы синхронизировать с React.
Рендер изолирован в `frontend/src/game/`: если персонаж начнёт ходить по миру, заменить придётся только этот модуль.

Тайлы 32×32, сад 16×10 тайлов. Сад рисуется с целым масштабом (×1/×2/×3) и `imageSmoothingEnabled = false`.

### 2. Локальный режим без авторизации
Один игрок создаётся автоматически, backend слушает только `127.0.0.1`. Кто «текущий игрок», решает
одно место в коде (`CurrentPlayer`), а все таблицы с самого начала привязаны к игроку.
Настоящий вход (Spring Security, BCrypt, cookie-сессия, CSRF) будет отдельным этапом до любого деплоя.

### 3. Рост растений от реального времени
Стадию растения сервер вычисляет при чтении: `planted_at` плюс длительности стадий вида. Фоновые задачи не нужны.
Растения не вянут и не погибают. Привычки дают ресурсы, а время в саду просто идёт, и дни отдыха ничего не ломают.

### 4. Защита от повторного начисления награды
- «Сегодня» вычисляет сервер по часовому поясу из профиля, клиент дату не передаёт.
- `habit_completion` имеет `UNIQUE (habit_id, completed_on)`: одна отметка в день на привычку.
- Отметка — идемпотентный `PUT …/completions/today`. Первый вызов возвращает 201 с наградой, повторный — 200 без награды.
- Вставка выполнения и начисление идут в одной транзакции. Если два запроса пришли одновременно, второй упирается в UNIQUE.
- Списания делаются атомарным `UPDATE … SET qty = qty - :n WHERE qty >= :n`, плюс `CHECK (… >= 0)` в базе.

### 5. Все ресурсы — в одном инвентаре
Семена жизни, осколки кристаллов, пакетики семян и (позже) Солнечные искры хранятся строками
`inventory_item`, различаясь видом предмета в каталоге (`CURRENCY`, `SHARD`, `SEED`, `DECOR`).
Поэтому у всех ресурсов одна атомарная операция начисления и списания и один `CHECK (quantity >= 0)`,
а награда описывается списком «предмет × количество». Новая валюта — это строка в каталоге, а не новая колонка.

### 6. Награда за привычку и дневной лимит
Отметка даёт 3 Семени жизни и 1 осколок категории привычки, если категория задана.
Первые 6 отметок за день приносят награду, следующие засчитываются без неё: так нельзя
нафармить ресурсы, создав 30 привычек «моргнуть». Все числа лежат в `game.rewards.*` в `application.yml`.
Каждая операция игрока над ресурсами блокирует строку его профиля (`SELECT … FOR UPDATE`),
поэтому параллельные запросы выполняются по очереди, и лимит считается без гонок.

### 7. Покупки с ключом идемпотентности
На каждое нажатие «Купить» клиент создаёт UUID и отправляет его в заголовке `Idempotency-Key`.
Пара (игрок, ключ) уникальна в `shop_purchase`. Если ответ потерялся в сети и игрок нажал ещё раз,
клиент отправит тот же ключ, а сервер вернёт уже сделанную покупку и не спишет второй раз (тот же приём, что у платёжных API).
Списание — один `UPDATE … WHERE quantity >= :cost`: баланс не может уйти в минус даже при параллельных запросах.

### 8. Java 17
Spring Boot 4 поддерживает Java 17+. На машине разработки полный JDK установлен только для 17
(Java 21 там без компилятора). Чтобы перейти на 21, достаточно поменять `java.version` в `pom.xml`.

### 9. Testcontainers для backend-тестов
Гарантии целостности держатся на PostgreSQL: UNIQUE, CHECK, блокировки строк. H2 ведёт себя иначе,
поэтому тесты идут на настоящем PostgreSQL в одноразовом контейнере.

## Модель данных вертикального среза

| Таблица | Ключевые поля | Ограничения |
|---|---|---|
| `app_user` | id, created_at | в локальном режиме одна запись |
| `player_profile` | user_id, display_name, timezone | |
| `crystal_category` | key, name, color, meaning | контент, 6 категорий |
| `habit` | id, player_id, title, crystal_category, created_at, archived_at | уникальное имя среди активных привычек игрока |
| `habit_completion` | id, habit_id, player_id, completed_on, life_seeds, shard_item_key | `UNIQUE (habit_id, completed_on)` |
| `plant_species` | key, name, stage_minutes[] | контент, заполняется миграцией |
| `item_def` | key, kind, price, species_key, crystal_category | контент; на категорию ровно один осколок |
| `inventory_item` | (player_id, item_key), quantity | `CHECK (quantity >= 0)` |
| `shop_purchase` | id, player_id, idempotency_key, item_key, quantity, cost | `UNIQUE (player_id, idempotency_key)` |
| `garden_object` | id, player_id, garden_key, x, y, kind, species_key, planted_at | `UNIQUE (player_id, garden_key, x, y)` |

Артефакты, рецепты, точки находок (см. [design/crystals.md](design/crystals.md)), квесты, расчистка участков,
декор и внешность персонажа добавятся следующими миграциями.

## API

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/state` | состояние игрока: «сегодня» по его поясу, инвентарь, привычки, награды дня, растения в саду со стадиями |
| GET | `/api/catalog` | категории кристаллов, виды растений, предметы с ценами, карта сада |
| POST | `/api/habits` | создать привычку `{ title, crystalCategory \| null }` → 201 |
| PUT | `/api/habits/{id}` | изменить название и категорию |
| DELETE | `/api/habits/{id}` | убрать в архив (полученные награды остаются) → 204 |
| PUT | `/api/habits/{id}/completions/today` | отметить «сделано сегодня»: 201 с наградой или 200, если уже было |
| POST | `/api/garden/plantings` | посадить `{ x, y, seedItemKey }` на свободную грядку → 201 с растением и стадией роста |
| POST | `/api/shop/purchases` | купить `{ itemKey, quantity }` с заголовком `Idempotency-Key: <uuid>`: 201 или 200 при повторе |
| GET | `/actuator/health` | жив ли сервер и есть ли связь с базой |

Ошибки всегда приходят в формате Problem Details (`{ title, status, detail }`).

## Сад на экране

- **Карта** — контент: `backend/src/main/resources/content/gardens/home.json`. Тайлы записаны строками
  символов, легенда описывает каждый символ (название, описание, можно ли сажать), постройки лежат поверх.
  Backend проверяет карту при старте (размеры, неизвестные символы, постройки за краем) и отдаёт её в `/api/catalog`.
- **Спрайты** — атлас `frontend/public/assets/atlas.png` + `atlas.json`. Сейчас их рисует скрипт
  `npm run atlas` (`frontend/scripts/build-placeholder-atlas.mjs`) по правилам [ART_DIRECTION.md](ART_DIRECTION.md).
  Чтобы подключить настоящую графику, достаточно заменить оба файла, сохранив имена кадров.
- **Рендер** — `frontend/src/game/`: `layout.ts` (чистая геометрия: кадр клетки, забор по соседям,
  клетка под курсором), `renderer.ts` (слои: земля → постройки → подсветка), `GardenCanvas.tsx` (React-обёртка).
  Масштаб целый ×1–×3, на телефоне дробный. Клетку можно выбрать мышью или стрелками.
  Сцена рисуется во внеэкранный буфер 1:1 и переносится на экран одним масштабированием, поэтому между тайлами нет швов.
- **Растения** хранятся в `garden_object` с `UNIQUE (player, сад, x, y)`. Стадию вычисляет `PlantGrowth`
  по `planted_at` и длительностям стадий вида. Клиент получает `nextStageAt` и в этот момент тихо перечитывает состояние.
  Посадка проверяет клетку по карте (грядка, не постройка, не занята), списывает пакетик и создаёт растение в одной транзакции.

## Контент

Растения и предметы — это данные, а не код. Они описаны в
`backend/src/main/resources/db/migration/R__content.sql`. Это repeatable-миграция:
Flyway перезапускает её при каждом изменении файла, а upsert обновляет существующие строки.
Чтобы добавить растение, достаточно дописать строки в этот файл, Java-код менять не нужно.

2. ✅ Каркас backend: Spring Boot, health, Problem Details, Testcontainers
3. ✅ Каркас frontend: Vite, React, TS, CSS Modules, палитра, раскладка, API-клиент
4. ✅ Игрок и контент: автосоздание локального игрока, каталог, `GET /api/state`
5. ✅ Привычки с категориями кристаллов, награда (Семена жизни + осколок), дневной лимит, уведомления
6. ✅ Лавка семян: покупка за Семена жизни, идемпотентность, защита от минуса
7. ✅ Canvas-сад: карта-контент, атлас временных спрайтов, наведение и выбор клетки (мышь и клавиатура)
8. ✅ Посадка, рост по стадиям, сквозная проверка с перезагрузкой страницы

**Кристаллы** ([design/crystals.md](design/crystals.md))
9. Первый рецепт (изумруд + аметист) и спящий магический объект в саду
10. Точка находки, первый артефакт, коллекция, Солнечные искры за значимое открытие
11. Общая проверка

**Отложено:** отмена отметки, еженедельные привычки, диалоги Мастера Вереска,
квесты, находки, декор, внешность персонажа, вторая зона, авторизация, деплой.
